# C23 特定 — judg（ジャッジメント）フェーズがターン毎リセットではなく戦闘通算連続（実機3/3裏取り）

> 2026-07-12 Claude Code。タスク②（C23特定）。**T4#19 judg「リキャストされていない」実機トラブル（raw_data2 欠陥2）の根本原因を特定**。
> ハーネス: scratchpad `c23.mjs`（sim02 追撃OFF順＝raw_data2 の押下番号に一致・計装replay）。

## 1. 決定的所見: 実機の judg フェーズは戦闘通算で連続

judg は3フェーズ循環（ph0=敵全体10回ダメージ「アビリティ」表示 / ph1=バースト / ph2=通常攻撃）。
**現sim は `ph = T.ju % 3` で、`T.ju` がターン毎に0リセット**（`_beginTurn`）＝各ターン必ず ph0 から始まる。
**実機は戦闘通算で連続**（ph0→1→2→0→1→2… ターンを跨いでも途切れない）。

実機の各ターン「最初の judg」のフェーズを raw_data2 のテトラ1表示から分類し、両モデルの予測と照合:

| ターン | 実機 最初のjudg（表示） | 実機ph | 通算連続モデル予測 | 現sim(リセット)予測 |
|---|---|---|---|---|
| T1 | アビリティ546万 | ph0 | ph0（通算0%3=0） ✓ | ph0 ✓ |
| T2 | アビリティ614万 | ph0 | ph0（通算3%3=0） ✓ | ph0 ✓ |
| T3 | アビリティ714万 | ph0 | ph0（通算9%3=0） ✓ | ph0 ✓ |
| **T4** | **バースト808万** | **ph1** | **ph1（通算13%3=1） ✓** | **ph0 ✗** |
| T5 | アビリティ865万 | ph0 | ph0（通算15%3=0） ✓ | ph0 ✓ |
| **T6** | **三段攻撃143万** | **ph2** | **ph2（通算20%3=2） ✓** | **ph0 ✗** |

実機の判定押下数（通算）: T1=3(→3) / T2=6(→9) / T3=4(→13) / T4=2(→15) / T5=5(→20) / T6=3。
**通算連続モデルが T4/T5/T6 の開始フェーズを 3/3 で的中**（T1〜T3は両モデル一致で非判別）。現sim のリセットモデルは **T4・T6 を外す**。

## 2. #19「リキャストされていない」との因果

- 実機 T4 は通算 ph1 始まり＝[ph1(バースト808万), ph2(通常129万)] の2押下で、**3押下目は ph0**（敵全体10回）になるはずだが実機は**押せなかった**（#19 ブロック）。
- 現sim T4 はリセットで ph0 始まり＝[ph0(#12), ph1(#17 バースト), ph2(#19 通常)] の3押下。
- **フェーズがズレると「どの judg 押下がバースト（ph1）か」がズレ、バースト発火位置＝コヴァレント・アルカナのバーストproc（`T.burst%2`）位置がズレ、judg の re-arm（`cd.judg=0`）タイミングがズレる**。
  sim 計装（c23.mjs T4トレース）では #17(ph1 burst) の2ndバーストprocが cd.judg=0 に再アームし #19 判定を通す。実機は ph 配置が違うため #19 時点で未アーム＝押下不可。
- ∴ **#19 の re-arm 位置ズレは、judg フェーズのターンリセット（本来は戦闘通算）という単一のモデル誤りの下流症状**。
  連理魔力（proc 回数）が実機と一致していた（T4 14→16・+2）のは、proc の総数は同じで**位置だけ**がズレていたため（C23起票時の「連理一致＝proc整列の残余」と符合）。

## 3. 原因の局在（コード）

- `data/characters.js` judg.exec: `const ph = T.ju % 3;` … `T.ju++`（フェーズをターン毎 `T.ju` から導出）。
- `src/sim.js` `_beginTurn`: `T = {..., ju:0, ...}`（毎ターン `T.ju` を0初期化）。
- `T.ju` は**二重用途**: (a) フェーズ `ph=T.ju%3` (b) 同ターン上限ガード `T.ju < judgCap`（`judgCap=JUDG_REACT + (開始cd===0?1:0)`）。
  (b) はターン毎リセットで**正しい**（同ターン発動回数の上限）。誤っているのは (a) のみ。

## 4. 修正方針（未実装・golden移動のため要ゴーサイン）

- **戦闘通算の judg 押下カウンタ**（例 `sim.judgPhase`・constructor で0初期化・**ターンリセットしない**・clone/snap で伝播）を新設。
  フェーズを `ph = sim.judgPhase % 3` から導出し、judg 押下毎に `sim.judgPhase++`。
- `T.ju` は**据置**（同ターン cap ガード・目的関数の判定回数カウントは現行のまま正）。
- 影響:
  - **golden 移動**（フェーズ再割当でどの judg がバースト/通常かが変わる＝ダメージ変化）＝C18/C19/C21 同様に raw/calibrated 再fit・`test/golden.mjs`・CLAUDE.md/AGENTS.md 検証ゲート・`ENGINE_VERSION` 更新が必要。
  - **最適押し順の変化**（探索が judg を正しい通算フェーズ前提で配置）。
  - ⚠ **`ENGINE_VERSION` bump は sim03 の追撃ON再探索キャッシュを無効化**＝sim03 実機取得前に**再探索が必要**（sequencing 判断事項）。
- 受入検証（実装時）: 修正後 replay で T4/T5/T6 の開始フェーズが実機（ph1/ph0/ph2）に一致し、#19 相当が未アームでブロックされること（sim も実機同様 T4 judg 2回）を確認。

## 5. 結論
- **C23 は root-cause 確定（判定フェーズのターンリセット・実機3/3裏取り）**。曖昧性なし＝実装可能な明確なfix。
- ただし golden ゲート移動＋sim03 キャッシュ無効化を伴うため、**実装のゴー/シーケンシングはユーザー判断**（本メモで提示）。
