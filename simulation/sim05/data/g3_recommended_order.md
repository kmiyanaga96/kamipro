### ✅ config 再現の検証（v2 の信頼性の根拠）

ユーザーキャッシュの `turnsKeys` を上記条件（**stale ATK のまま**）でリプレイし、記録値と **完全一致**：

```
再生値 1,853,003,034 / 記録値 1,853,003,034 → ✅ bit 一致
```

∴ サブ枠・英霊武器・敵設定・GEAR は**ユーザー環境と同一**であることが確定。v2 はここから **ATK だけを configC 実機値へ差し替えて**再探索した結果＝stale ATK の影響のみを分離できている。

### ⚠ 留保（実走の解釈に必要）

1. **override は stale ATK 下で較正された値**を流用（`{pactcore:1, effond:120}`）。UIで再探索すれば較正もやり直される＝そちらがより正確。
2. **10T総ダメージ最大化であって撃破速度の最適化ではない**（kill-turn は未実装）。「最速撃破の順」とは限らない。
3. **buffCount 過大の影響下**（`buffcount_sim_side_diag.md`）。ナポの4アビは全て buffCount 閾値でスコアが切り替わるが、シムは**全 tier を T1 から常時到達**と誤認している。本順は「pike 確実会心・consort 2hit・roy 最上位tier・factor 全体CD-1 が常にON」前提での最適化＝**この前提の当否が実走 §B の測定対象**。

## 5. 実走時の注意

- **押せない手が出たら §A に逸脱理由を記録**（CD残/ゲージ不足/対象不在/UI不可/生存優先）。シムが CD・ゲージ経済を誤っていれば、そこが構造バグの一次情報になる。
- **生存を優先して順を崩すのは正しい**。シムは火力最適化のみで**回復・状態異常回復を目的関数に持たない**＝返る順は火力スケルトン。崩した箇所を記録すれば足りる。
- **アビ20回目を押さない**（鬼神一擲＝バフ全消去＋特大）。本順は全ターン19手ちょうど＝追加で押す余地はない設計。
- §B の tier 観測は**この順の前提そのものの検証**＝最優先で記録する。

## 6. 経緯（v1 撤回の記録・同種ミスの再発防止）

- **v1（撤回）**: サブ枠未設定・英霊武器未反映で抽出（7T地平・prefix `[pike]`・T6撃破）。ユーザーキャッシュの記録値 1,853,003,034 に対しリプレイが 1,540,924,940 にしかならず発覚。
- **原因**: `betaia_mult/cap`・`napo_burst_cd_reduce`・`CURRENT_SUBS` は **`_configSig` に含まれない**ため、キャッシュJSONを読むだけでは検出できない。とくに `napo_burst_cd_reduce`（バーストで自身の全アビCD-1）は**押せるアビが変わる＝押し順そのものを変える**。
- **教訓**: headless で config を再現する際は、**ユーザーキャッシュの `turnsKeys` をリプレイして記録 `dmg` と bit 一致することを必ず先に検証**してから探索を回す（署名一致だけでは不十分）。
