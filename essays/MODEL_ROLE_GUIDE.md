# モデル役割分担ガイド — Sonnet / Opus / Fable を本PJでどう使い分けるか

> **この文書について**: essays/（開発体系外の自由文書）の運用ガイド。CLAUDE.md のドキュメント体系には属さず、
> 参照義務もない。価格・モデル仕様は **2026-07-22 時点**（価格は変動するため、大きな判断の前に最新を確認すること）。
> 対象読者は本PJのオーナー（実機オラクル担当）と、セッションを跨いで作業する Claude Code 自身。

## 0. 結論（一行）

**「間違いが実機データを無駄にする判断」は Fable、「手を動かす」は Opus、「写して整える」は Sonnet。切替はセッション境界で。**

- 長セッションの実コストは**出力トークンとキャッシュ書込が支配**（キャッシュ読みは約0.1×）。

## 2. 本PJの費用構造 — なぜ「ケチる場所」を間違えてはいけないか

このPJの律速資源は**AIのトークン代ではなく、オーナーの実機プレイ時間**である。

- sim03 の実機第1バッチ（D×5・全hit毎記録）は取得に数時間かかり、**取り直しは同額の人的コスト**。
- それを解釈する統合分析セッションのトークン代は、Fableで走らせても高々数ドル〜十数ドル。
- ∴ **分析の質を1段上げる（＝誤った較正判断で実機バッチを無駄にする確率を下げる）ためのモデル格上げは、
  常に採算が合う**。逆に、定型作業をFableで回すのは純粋な無駄。

過去実績が示す「1観測の重み」（付録A.4／ENGINE_CHRONICLE）: C23はターン頭judg演出の目視**3件**でgolden −8.4%の
是正を確定した。観測1件の解釈を誤ればgolden数百万〜数千万相当の較正が狂う。**判断の単価はトークン単価より桁で重い。**

## 3. 役割マップ（本PJの具体タスクで例示）

### Fable 5 — 「間違うと実機データが無駄になる判断」

| タスク種別 | 本PJでの具体例 |
|---|---|
| 統合分析・較正判断 | sim04 `integrated_analysis.md`（C25 raw枠帰属の確定・絶対レベルスカラの推定・golden再fitの採否＝実際に abs スカラを fit した回） |
| 仮説の設計と棄却 | B5型の定量テスト設計（「cap外し」仮説をθ不整合で棄却した類）・識別不能性の検出（モデルと敵耐性の同時fit禁止の類） |
| 探索/エンジンのアーキテクチャ判断 | C27の機構選定（orthodoxy案・静的スコア案を「原理的に効かない」と棄却して局所改善を採用した判断） |
| 罠の多い交絡推論 | C15型の「同一レバーが新モデル+9.6%/旧モデル−6.5%」の見抜き・sim03の系統交絡の層別設計 |
| 高品質の文章 | essays/ の読み物・重要ドキュメントの書き下ろし |

**使い方のコツ**: タスク仕様を最初のターンで完全に与える（途中で小出しにしない）。1リクエストが数分に及ぶ
ことがあるのは正常。thinking は常時ONなので指定不要。

### Opus 4.8 — 日常のデフォルト（実装・検証・運用）

| タスク種別 | 本PJでの具体例 |
|---|---|
| 実装 | `CHAR_REGISTRY`への新キャラ宣言・`_refineRoute`のようなエンジン改修・D10（worker自動diff化）型のリファクタ |
| 検証・再fit | golden再fit・`c27_refine_probe.mjs`のようなハーネス作成と実行・buildとreplay照合 |
| デバッグ | 乖離の再現スクリプト作成・反実仮想リプレイ（C27の発見過程はこの粒度） |
| リポジトリ運用 | 整理（A1/B2-B4型）・ドキュメント体系の同期・コミット/マージ/プッシュ |

**使い方のコツ**: 本PJの実装は「golden不変 or 意図した変動のみ」という強い検証ゲートがあるため、
Opusで十分に安全。急ぎの対話的作業には fast mode（Opus限定）という選択肢もある。

### Sonnet 5 — 定型・機械的作業（特に導入価格中はお得）

| タスク種別 | 本PJでの具体例 |
|---|---|
| データ転記・整形 | trialXX.md の記入内容チェック・スケルトンからの表整形・スクショのテキスト転記の清書 |
| 一次集計 | sim03 D×5受領後の**決定性突合の全数表**・成分別集計・max_hp回帰の計算実行（解釈はしない） |
| ドキュメント同期 | README表の更新・リンク修正・記録テンプレの複製 |
| 軽い調査 | grep調査・「この値はどこで定義されているか」型の探索 |

**使い方のコツ**: quantitative_analysis の「演算部分」はSonnetで走らせ、**数字の解釈と結論はFable/Opusの
セッションに渡す**分業が効く（P3形式=手法/入力の明記があるため引き継ぎが安い）。

### Haiku 4.5 — 本PJでは非推奨

CLAUDE.md＋較正文脈の常時読解が必要な本PJでは、節約幅（対Sonnet）よりミス修正コストが上回りやすい。
使うなら「単一ファイルの機械的変換」など文脈不要の作業に限る。

## 4. 運用ルール

### 4.1 切替はセッション境界で（キャッシュ毀損の回避）

プロンプトキャッシュは**モデル別**。セッション途中で `/model` を切り替えると、次のリクエストは会話履歴
全体のキャッシュを書き直す（読み0.1×→書き1.25×へ逆戻り）。長セッション（数十万トークン級）でメッセージ
単位のfable⇄opus往復をすると、**切替のたびに再キャッシュ代が乗る**。

- ❌ 1セッション内で分析はfable・実装はopusと往復する
- ✅ 「Sonnetで一次集計セッション → Fableで統合分析セッション → Opusで実装セッション」とタスク境界で区切る

### 4.2 統計的較正バッチ処理の推奨レシピ（simNN 共通の実用形）

```
trial01〜05 受領
  │
  ├─ [Sonnet] 一次集計セッション
  │    転記検証・決定性突合表・成分集計・max_hp回帰の計算
  │    → quantitative_analysis.md の「表」を埋める（解釈は書かない=P3形式そのまま）
  │
  ├─ [Fable] 統合分析セッション
  │    定量+定性を読み込み → C25帰属判断・絶対レベル推定・較正案の確定
  │    → integrated_analysis.md・モデル修正の設計
  │
  └─ [Opus] 実装セッション
       DMG/CHAR_REGISTRY修正・golden再fit・CALIBRATION更新・コミット/マージ
```

1バッチあたりの目安コスト: Sonnet数十セント〜・Fable数ドル〜十数ドル・Opus数ドル。
**合計しても実機D×5の再取得コスト（人的時間）の2桁下**。

### 4.3 迷ったときの判定基準

1. **この判断を誤ると実機バッチを取り直すか？** → YES なら Fable。
2. **golden/build/replayで機械的に検証できるか？** → YES なら Opus で十分。
3. **出力の形式が事前に完全に決まっているか？**（表を埋める・テンプレを写す） → YES なら Sonnet。
4. 判定に迷う境界例は**上のモデルに倒す**（このPJでは判断ミスの方が高くつく）。

本ガイド執筆時点のセッションで実際に行った作業を事後分類すると:

| trial01テンプレ作成・記録スケルトン | Sonnet | 形式が決まっている |
| リポジトリ整理の走査と提示 | Opus | |

実際にはメッセージ単位で fable⇄opus を往復した（＝キャッシュ毀損あり）。**次回以降はセッション境界方式へ**。
